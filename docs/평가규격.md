# 평가 규격 (C)

평가는 정답 라벨과의 일치로 잰다. 답변 문장이 정답 문장과 얼마나 비슷한지는 보지 않는다. 생신 상한 25만 원(V1)과 22만 원(V2)처럼 문장은 거의 같고 답만 다른 경우가 이 규약집에 많기 때문이다.

## 출력 형식

항목 순서는 규약집 표 05의 판단 순서를 따르고, 상태는 뒤쪽에 둔다. 모델이 근거와 조건을 먼저 쓴 뒤 판정하게 하려는 것이다.

```json
{
  "개정_항목": "손님 숙박",
  "기준일_종류": "숙박 시작일",
  "기준일": "2026-12-05",
  "적용_판본": "V3",
  "조건": {"사전_합의": "있음"},
  "근거": [
    {"출처": "표 07", "행": "손님 숙박", "쪽": 7},
    {"출처": "부칙 제1조", "행": null, "쪽": 53},
    {"출처": "표 56", "행": "2박", "쪽": 56},
    {"출처": "표 44", "행": "2박", "쪽": 44}
  ],
  "상태": "가능",
  "답": "예, 숙박 절차를 충족합니다.",
  "다음_행동": "정해진 방식으로 기록한다",
  "추가_확인_질문": null
}
```

위는 gemma4-31b가 V3 문서로 실제 낸 답이다(공개 문항 PUB-085, 일부 칸 생략).

| 항목 | 허용 값 |
| --- | --- |
| 상태 | 가능 / 사전 합의 필요 / 공동 처리 불가 / 추가 확인 / 규정에 없음 (규약집 표 06) |
| 적용_판본 | V1 / V2 / V3 / 해당 없음 / 미정 |
| 근거 | 항상 목록. 조항 `제23조`, 표 `표 41`, 부칙 `부칙 제3조` |
| 추가_확인_질문 | 상태가 '추가 확인'일 때만 문장 |

## 지표

| 지표 | 채점 방식 |
| --- | --- |
| 주지표(판정 정확도) | 상태와 적용 판본이 **둘 다** 맞으면 1점 |
| 근거 인용 정확도 | 근거 채점 대상 문항에서 필수 근거의 `;` 묶음마다 `\|` 후보 중 하나 이상을 인용하면 1점 |
| 개정 대응 | 개정 전후 쌍에서 두 문항 모두 상태·판본을 맞혀야 1쌍 |
| 경량화 효과 | 파일 크기, 가중치 메모리 |
| 응답 시간 | 요청부터 답변 완료까지(중앙값, p95) |
| 잘림 | 최대 출력 토큰 안에 JSON을 끝내지 못한 문항 수 |

## 필수 근거 규칙: '판정을 가르는 것만'

- 넣는 것: 질문의 값(금액·날짜·시각·합의 여부)과 실제로 비교한 기준의 출처, 금액을 합치거나 빼는 계산 규칙의 출처
- 빼는 것: 비교에 쓰지 않은 출처, 모든 판본 문항에 공통인 부칙 제1조
- 같은 기준값이 여러 곳에 있으면 어느 쪽을 인용해도 인정(예: 생신 상한은 부칙 제3조와 표 54)
- 정답이 '추가 확인'인 문항은 근거 채점에서 제외

이유: 과제가 묻는 것은 판단력이다. '확인하라고 한 것 전부'로 채점하면 꼼꼼함을 재게 되고, 작은 모델이 긴 목록을 빠뜨리는 것이 판단 차이처럼 보인다.

## 실패 원인을 따지는 순서

1. JSON이 깨졌는가 → 형식 깨짐
2. 검색 결과에 필수 근거가 있었는가 → 없으면 검색 실패
3. 개정 항목 · 기준일 종류 · 적용 판본이 맞는가 → 판본 오선택
4. 금액 · 날짜 · 합의 여부를 맞게 읽었는가 → 독해 문제
5. 위가 다 맞는데 상태가 틀렸는가 → 추론 문제

## 숫자를 읽을 때

- 150문항에서 1문항은 0.7%p, 봉인 50에서는 2%p. 한두 문항 차이는 우열로 단정하지 않는다
- 바꾼 조건이 하나인 실험끼리만 원인을 말한다
- 19개 모델 비교의 95% 구간은 상황 단위 부트스트랩(변형 문항을 같은 상황으로 묶음)
